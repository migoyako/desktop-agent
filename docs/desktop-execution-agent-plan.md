# 受控桌面执行代理功能计划

- 版本：v0.1
- 日期：2026-11-04
- 状态：关键决策已确认，等待接口探测与开发切片拆分
- 范围：Windows 桌面端、现有 Companion 应用、OpenClaw/微信入口、通用中转启动链

## 1. 目标

把当前以对话、记忆和笔记写入为主的 Companion，扩展成能安全操作本机资源的桌面执行代理。

第一版需要完成三类用户场景：

1. 打开本机应用、文件夹和文档。
   - 例如“打开回收站”“打开腾讯会议”“打开桌面的项目说明”。
2. 在微信中收发文件并操作本机文件。
   - 例如“把上次的项目周报发给我”“把这张图片保存到项目素材目录并改名”。
3. 通过中转应用启动目标应用，并继续执行目标应用支持的后续动作。
   - 例如“通过 Codex++ 启动 Codex，在项目 A 中找到对应会话，把优化指令传进去”。
   - 同一能力也要能适配其他借助启动器、IDE、游戏平台、远程客户端或项目面板启动的工具。

## 2. 产品原则

- 模型只能调用定义明确的工具，不能直接拼接 Shell 命令。
- 所有本机能力必须先有授权，并绑定到具体目录、应用或工作流。
- 读操作和外部副作用分开授权。
- 写入、跨会话发送、删除、界面控制和远程指令注入必须可审计。
- 模型回复不是执行证据，界面和执行层只相信执行器回执。
- 模糊的文件、应用、会话或聊天对象不能猜测，必须让用户选择。
- 不能撤销的动作必须在执行前明确说明。
- 默认不永久删除文件，删除只进入 Windows 回收站。
- 个人微信桌面 UI 自动化只能作为降级适配，不作为第一版主通道。

## 3. 总体架构

```text
桌面界面 / OpenClaw 微信 / 后续聊天通道
                    |
                    v
         统一应用服务与任务编排
                    |
        +-----------+-----------+
        |           |           |
        v           v           v
   能力授权中心   动作提案     执行账本
        |           |           |
        +-----------+-----------+
                    |
    +---------+---------+---------+---------+
    |         |         |         |         |
    v         v         v         v         v
 文件系统   应用启动   聊天媒体   UI 自动化  Codex 工作流
```

现有 `agent_service.py` 连接的是旧 `ChatAgent`，与 Companion 应用服务是两条独立链路。实施时应先把聊天入口接到统一的 Companion 应用服务，避免文件、审批和回执能力各做一套。

## 4. 核心模块

### 4.1 授权中心

支持以下授权类型：

- 文件读取目录。
- 文件写入目录。
- 文件搜索目录。
- 允许外发的目录和文件类型。
- 允许启动的应用。
- 允许自动操作窗口的应用。
- 允许运行的中转启动链。
- 允许接入的微信用户和会话。

每个授权至少保存：

- 授权对象身份。
- 权限范围。
- 创建和最后使用时间。
- 当前状态。
- 撤销入口。

目录授权保存规范化路径、卷标识和文件标识。目录身份变化后必须重新授权。

授权交互采用“先配置常用资源，任务中按需补权”的方式：

1. 首次设置由用户主动完成，不阻塞普通对话。
2. 用户选择常用目录时使用 Windows 原生目录选择器，并分别勾选读取、写入、搜索和外发能力。
3. 应用目录扫描后只展示候选，用户勾选的应用才进入允许启动清单。
4. 项目开发可以创建一次“项目授权包”，包含项目目录、默认中转启动链和默认目标应用。
5. 任务缺少权限时，只弹一张合并授权卡，不按动作连续弹窗。

授权卡需要写明：

- 当前任务为什么需要权限。
- 具体目录、应用或启动链。
- 请求的能力和不会获得的能力。
- 授权有效期。
- “仅本次”“本项目”“永久”和“取消”选项。

推荐提供以下快捷模板：

- 打开应用：只授予指定 `app_id` 的启动权限。
- 项目开发：项目目录读取和写入、指定中转启动链、目标应用工作流。
- 接收附件：只允许附件进入隔离收件箱，不自动获得项目目录写入权限。
- 发送文件：只允许从指定目录向当前聊天发送，不授予其他聊天对象。

永久授权不等于永久放行所有动作。文件覆盖、跨会话发送、UI 输入、永久删除和无法撤销的远程操作仍然逐次确认。

任务开始时签发短期授权租约：

```text
grant_lease(
  grant_id,
  task_id,
  capability,
  resource_ids,
  expires_at,
  max_operations,
  nonce
)
```

租约绑定任务、资源身份和确认指纹。任务结束、用户撤销、资源身份变化或超过有效期后立即失效。

### 4.2 文件搜索与操作

第一版支持：

- 列出目录。
- 读取文件元数据和受支持文件内容。
- 按文件名、路径、类型、修改时间搜索。
- 可选的内容索引。
- 新建、覆盖、复制、移动和重命名。
- 删除到 Windows 回收站。

文件搜索只覆盖授权目录。模型只接收少量候选，不接收完整文件清单。

索引策略分为三层：

- 文件元数据索引：保存文件名、规范化路径、父目录、扩展名、大小、修改时间、文件身份和索引状态。
- 浅层目录摘要：只保存授权根目录和少量层级的目录数量、文件数量和最近更新时间，用于界面展示和缩小搜索范围。
- 可选全文索引：只对用户明确允许的文本格式建立，原文和片段继续留在本机。

授权目录后异步建立索引，并显示“正在建立索引”的进度，不要求用户等待全部完成后才能开始普通对话。索引建立期间可以退化为有上限的实时搜索。

后续搜索先查本地索引。只有少量候选和命中片段进入模型上下文，禁止把完整目录结构文档整体注入提示词。

如果用户需要查看目录全貌，界面只按层级展开当前目录并显示数量摘要。完整目录树可以作为本地索引的派生视图，不作为模型上下文中的一份长期文档。

索引 freshness 处理：

- 文件系统事件或 Windows USN Journal 可用时增量更新。
- 授权目录重新连接或事件记录不连续时执行后台对账。
- 搜索命中后执行前再次检查文件是否存在以及身份是否变化。
- 删除或移出授权目录的文件从可搜索集合中移除。

文件候选至少包含：

- 文件引用 ID。
- 文件名。
- 所在授权目录。
- 相对路径。
- 类型和大小。
- 修改时间。
- 命中原因。

多个候选时返回最相关的三条并要求选择。

文件修改必须经过：

```text
生成提案
→ 展示目标、哈希、影响范围和 Diff
→ 用户确认
→ 再次校验文件状态
→ 执行
→ 生成回执
→ 可撤销时提供撤销
```

### 4.3 应用与文档打开

新增全局应用目录，来源包括：

- 开始菜单快捷方式。
- Windows App Paths 注册表。
- UWP/MSIX 应用。
- 用户手动登记的应用。
- 系统特殊位置。

应用目录只负责发现和索引，不代表自动授权。用户从目录中把应用加入允许启动清单后，模型才能看到并调用它。

应用目录条目至少保存：

- 稳定 `app_id`。
- 显示名称和别名。
- 启动目标类型：可执行文件、URI、Shell 特殊位置或 UWP AUMID。
- 规范化的可执行路径、URI 或 AUMID。
- 发布者或代码签名身份。
- 固定参数模板。
- 发现来源。
- 是否已加入允许启动清单。
- 最后校验时间和身份摘要。

模型只能调用 `open_app(app_id)`、`open_app(app_id, document_ref)` 或 `open_path(file_ref)`，不能传入任意可执行文件路径和原始命令行。

Codex++ 与其他应用一样只登记一次。用户说“打开 Codex++”时，直接按应用目录中的 `app_id` 启动，不需要进入启动链，也不需要每个项目重复填写 Codex++ 路径。

需要支持：

- 回收站。
- 腾讯会议等普通桌面应用。
- 系统文件夹和用户授权目录。
- 文档通过 Windows 默认关联程序打开。

首次登记自定义应用需要确认。应用路径、发布者或版本身份发生变化后重新确认。

可执行文件、脚本、包含宏的文档和未知高风险管理文件默认不通过“打开文档”直接执行。

### 4.4 微信文件通道

优先使用 OpenClaw 的聊天和媒体能力，通过通道适配器接入。

入站流程：

```text
微信消息与附件
→ 验证发送者和会话
→ 下载到隔离收件箱
→ 检查大小、扩展名、魔数、哈希和文件名
→ 登记附件
→ 等待用户指定后续操作
```

出站流程：

```text
用户要求发送文件
→ 只搜索授权目录
→ 返回候选或选定唯一文件
→ 校验文件仍在原位置且哈希未变化
→ 发送到发起命令的当前会话
→ 保存通道消息 ID 和文件哈希
```

明确文件名、唯一命中且发回原会话可以直接执行。以下情况必须确认：

- 多个文件命中。
- 目标聊天不是发起命令的会话。
- 批量发送。
- 文件位于高敏感目录或属于受限类型。
- 文件在搜索后发生变化。

微信会话必须绑定允许的用户和聊天 ID。未知用户不能触发本机能力。

### 4.5 中转启动链

Codex++ 只是启动链的一个实例。通用目标是：Agent 启动一个中转应用，识别它最终启动的目标应用，并确认目标应用已经可用。

启动链至少包含：

- `chain_id`：启动链 ID。
- `starter_app_id`：第一个启动的中转应用。
- `target_app_id`：最终要启动和识别的目标应用。
- `trigger_kind`：自动启动、参数、URL Scheme、API 或 UI 操作。
- `trigger_config`：固定参数模板、控件路径或接口配置。
- `detection_rules`：如何确认目标应用确实已经启动。
- `readiness_rules`：如何确认目标窗口或服务已经可用。
- `post_launch_adapter`：可选的项目打开、会话恢复、指令注入等后置动作。
- `timeout_and_failure_policy`：等待时间、重试和人工接管条件。

触发方式：

- `auto`：启动中转应用后，它会自动启动目标应用。
- `argument`：向中转应用传入经过校验的目标参数。
- `uri`：通过固定 URL Scheme 打开目标。
- `api`：通过本地 CLI、插件、COM 或 IPC 启动目标。
- `uia`：通过 Windows UI Automation 选择并点击目标。
- `manual`：无法自动触发时，提示用户完成一次点击后继续检测。

启动链分为三类：

- 自动链：中转应用启动后自动产生目标进程，通用引擎无需专用代码。
- 触发链：需要通过参数、URI、API 或 UI 控件启动目标，需要保存触发配置。
- 后置工作流：目标启动后还要打开项目、恢复会话或传入指令，需要专用适配器。

目标应用检测不能只看进程名，至少组合以下证据：

- 启动前后进程树变化。
- 父进程和子进程关系。
- 可执行文件规范路径。
- 发布者或代码签名身份。
- 窗口类、标题和窗口句柄。
- URL Scheme 或文件关联。
- 本地服务端口、IPC 或健康检查。
- 启动时间与前台窗口变化。

同一中转应用可以配置多条启动链，指向不同目标应用。一条启动链也可以跨越多个中转进程，但每个目标都必须在全局应用目录中有稳定身份。

如果目标应用是单实例并复用启动前已有的进程，启动链必须显式声明 `reuse_existing` 检测规则，并校验目标身份与窗口变化。不能把任意旧实例当作本次启动成功。

推荐执行顺序：

```text
校验启动链授权
→ 校验中转应用和目标应用身份
→ 记录启动前进程与窗口快照
→ 启动中转应用
→ 按 trigger_kind 触发目标
→ 等待目标进程、窗口或服务出现
→ 排除启动前已存在的旧实例
→ 确认唯一目标实例
→ 执行可选的后置适配器
→ 保存中转进程、目标进程和窗口回执
```

实例不唯一时不能猜测。Agent 应列出候选进程、窗口标题和启动时间，让用户选择或停止任务。

通用引擎优先完成“启动并检测”。对于 Codex 这类工具，再叠加专用后置适配器：

```text
启动 Codex++ 启动链
→ 确认 Codex 目标进程和窗口
→ 打开指定项目
→ 查找已有会话
→ 会话不唯一时要求选择
→ 注入指令
→ 验证指令已进入输入框或已创建任务
```

自动化接口优先级：

1. 中转应用或目标应用官方 CLI、URL Scheme 或 API。
2. Windows UI Automation 控件操作。
3. 剪贴板和键盘注入。
4. 坐标点击或截图识别，仅作特定版本的降级适配。

UI 自动化必须以窗口进程、窗口标题和控件路径作为身份依据，不能只依赖屏幕坐标。执行过程中要支持全局停止和用户接管。

建议提供一次“录制启动链”流程：

1. 从允许启动清单选择中转应用。
2. 选择自动启动、参数、URI、API 或 UI 操作。
3. 手动执行一次，让系统记录进程、窗口和控件变化。
4. 从检测到的候选中指定目标应用。
5. 配置就绪条件和超时。
6. 保存并测试启动链。

录制只生成待审核配置，不会自动获得启动或 UI 控制权限。

### 4.6 快速安全启动协议

启动链执行采用“预检、封装、执行、验证”四段式，避免模型逐步试错。

```text
识别用户意图
→ 解析已知项目与启动链
→ 并行收集必要信息
→ 生成一次性密封执行计划
→ 如有缺失权限则合并确认
→ 执行器按固定步骤启动并等待
→ 校验目标应用和目标工作流
→ 返回回执
```

预检阶段只并行执行无副作用检查：

- 项目目录是否存在且仍在授权范围内。
- 中转应用和目标应用是否仍在允许清单中。
- 应用路径、发布者或身份摘要是否变化。
- 启动链是否启用，目标应用是否有对应适配器。
- 目标应用是否已经运行。
- 所需会话、项目或文件引用是否存在。
- 当前模式、权限租约和确认是否有效。

启动阶段串行执行有依赖的步骤：

- 记录启动前进程与窗口快照。
- 启动中转应用。
- 执行已登记的触发方式。
- 等待目标进程、窗口或服务出现。
- 校验实例唯一性和目标身份。
- 执行项目、会话或指令后置动作。

执行计划在启动前计算摘要并冻结。中转应用、目标应用、参数、工作目录、确认指纹或权限租约在确认后发生变化时，整个计划停止，不允许执行器自行换一条路径继续。

速度优化遵循以下规则：

- 文件搜索先查索引，不直接遍历整个授权目录。
- 只读取任务需要的元数据，正文按需加载。
- 多个独立的只读检查并行执行，有依赖的启动动作保持串行。
- 应用和启动链使用持久缓存，但每次执行前复核身份。
- 等待采用进程事件、窗口事件或有限轮询，不使用固定长时间睡眠。
- 目标应用已经在运行且身份匹配时，按启动链的 `reuse_existing` 规则复用。
- 确定性步骤由启动协调器一次执行，不要求模型每个步骤都重新发起工具调用。

执行期间向界面推送以下状态：

```text
正在检查权限
→ 正在启动中转应用
→ 正在等待目标应用
→ 正在打开项目
→ 正在定位会话
→ 已完成
```

任何阶段超时、实例不唯一、权限变化或目标身份不符时立即停止，并明确区分“没有启动”“可能已启动但无法确认”和“已经启动”。

### 4.7 统一任务编排

需要把用户请求路由到以下结果：

- 普通对话。
- 文件搜索。
- 文件修改提案。
- 应用或文档打开。
- 微信附件处理。
- 中转启动链。
- 目标应用工作流，例如 Codex 会话与指令注入。
- 追问补充信息。

多步骤任务必须保留中间状态。例如：

```text
查找文件
→ 等待用户选择
→ 生成发送提案
→ 等待确认
→ 发送并保存回执
```

切换会话、应用变化、文件变化或确认过期后，旧的中间状态不能继续执行。

## 5. 权限模型

建议新增或区分以下能力风险：

- `fs-read`：读取授权文件。
- `fs-write`：创建、覆盖、移动和重命名。
- `fs-delete`：删除到回收站。
- `app-launch`：启动已登记应用。
- `ui-control`：操作其他应用窗口。
- `chat-send`：向聊天会话发送文件。
- `launch-chain`：执行已登记的中转启动链。
- `workflow-run`：执行目标应用的会话、项目和指令工作流。
- `external`：现有 MCP 远程工具。

模式建议：

| 能力 | 陪伴 | 工作 | 执行 |
| --- | --- | --- | --- |
| 文件读取 | 禁止 | 允许授权目录 | 允许授权目录 |
| 文件写入 | 禁止 | 确认后执行 | 确认后执行 |
| 应用打开 | 禁止 | 已登记应用直接执行 | 已登记应用直接执行 |
| UI 自动化 | 禁止 | 每次确认 | 每次确认 |
| 聊天发文件 | 禁止 | 唯一命中可直发 | 唯一命中可直发 |

## 6. 数据模型

建议新增：

## 8. 验收场景

1. 输入“打开回收站”，系统打开 Windows 回收站。
2. 输入“打开腾讯会议”，系统启动已登记应用；未安装时给出明确原因。
3. 输入“打开项目说明”，唯一命中时打开文档；多个命中时返回候选。
4. 首次打开项目时，一张授权卡同时说明目录读写、启动链和默认目标应用，用户可选择“仅本次”或“保存到项目”。
5. 在微信输入“把项目周报发我”，系统找到唯一文件并发送到当前会话。
6. 从微信发送一张图片，系统保存到隔离收件箱，并允许随后移动到授权目录。
7. 输入“通过 Codex++ 启动 Codex”，系统完成并行预检、启动中转应用、确认 Codex 目标进程和窗口，并保存完整启动链回执。
8. 输入“用 Codex++ 打开项目 A 并传入优化指令”，系统在启动链成功后定位会话、注入指令并验证。
9. 配置另一条“中转应用启动目标应用”的启动链，系统不需要新增 Codex 专用代码即可完成启动和检测。
10. 目标应用窗口不可用或会话不唯一时，任务停在明确状态，不伪造完成回执。
11. 文件确认前被其他程序修改时，系统停止执行并要求重新生成提案。

## 13. 工程实现蓝图

### 13.1 实施依赖顺序

模块必须按以下依赖顺序实现：

```text
授权与资源身份
→ 文件索引与只读工具
→ 文件写操作执行器
→ 应用目录与直接启动
→ 通用启动链与目标检测
→ 目标应用工作流适配器
→ OpenClaw 聊天与附件通道
→ 统一自然语言编排
```

不能先让模型直接调用通用 UI 自动化，再补授权和执行账本。所有能力必须先进入资源目录和执行器，再向模型注册工具。

### 13.2 模块边界

建议新增或扩展以下模块：

| 模块 | 职责 |
| --- | --- |
| `access_control.py` | 多目录授权、应用授权、启动链授权、任务租约与撤销 |
| `file_catalog.py` | 文件元数据索引、增量更新、候选搜索和文件引用 |
| `file_actions.py` | 保留现有笔记写入；增加通用文件动作执行器 |
| `app_catalog.py` | 应用发现、允许启动清单、应用身份校验 |
| `launch_chain.py` | 启动链解析、预检、进程树/窗口检测和回执 |
| `desktop_uia.py` | Windows UI Automation 适配、控件路径校验与接管 |
| `channels/openclaw.py` | OpenClaw 文本、附件、用户和会话映射 |
| `workflows/codex.py` | Codex 项目、会话和指令注入适配器 |

路径安全和目录身份校验目前位于 `file_actions.py`。实施时应把通用部分提取为共享的路径安全模块，并让笔记写入和通用文件操作共同使用，避免两套安全规则漂移。

### 13.3 数据库迁移

新增 schema v13，至少包含：

- `access_grants`：目录、应用、启动链和聊天授权。
- `grant_leases`：任务级短期授权。
- `file_catalog`：文件元数据、父目录、文件身份、索引时间和删除状态。
- `app_catalog`：应用身份、别名、启动目标、发布者、允许状态和参数模板。
- `launch_chains`：中转应用、目标应用、触发配置、检测与就绪规则。
- `channel_bindings`：聊天通道、用户和会话绑定。
- `attachments`：入站/出站附件、哈希、隔离路径和通道回执。

迁移要求：

- 现有 `workspace_grants` 的单目录授权迁移为一条 `access_grants` 记录。
- 在旧调用方全部切换前保留 `get_workspace()` / `set_workspace()` 兼容。
- 现有 `write_note` 和 MCP 执行路径保持可运行。
- 新表同步加入备份、导出、完整性检查、全量删除和索引检查名单。

### 13.4 工具与应用层契约

模型可见工具建议保持少而稳定：

| 工具 | 风险 | 行为 |
| --- | --- | --- |
| `find_files` | `fs-read` | 查询本地索引，最多返回 5 个候选 |
| `read_file` | `fs-read` | 读取授权目录内的文件，带字符和大小上限 |
| `open_app` | `app-launch` | 启动允许清单中的 `app_id` |
| `open_path` | `fs-read` | 打开授权目录中的文件或文件夹 |
| `run_launch_chain` | `launch-chain` | 执行已登记的启动链 |
| `write_file` | `fs-write` | 只生成文件写入提案 |
| `move_file` | `fs-write` | 只生成移动或重命名提案 |
| `send_chat_file` | `chat-send` | 只生成向明确会话发送文件的提案 |

文件工具只接受 `file_ref`、目录授权 ID 和应用 ID，不接受任意绝对路径或命令行。应用服务需要提供对应的授权、索引、候选、启动链和回执查询方法，Web 和聊天通道共用同一套方法。

建议新增公开 API：

```text
GET/POST /api/access
GET      /api/files/search?q=...
POST     /api/files/inspect
GET/POST /api/apps
GET/POST /api/chains
POST     /api/chains/run
POST     /api/channels/openclaw/message
```

具体请求和响应使用 dataclass/字典契约，不直接暴露 SQLite 行。

### 13.5 执行器

现有 `confirm_proposal()` 已有笔记和 MCP 两类执行路径。继续增加分支会让确认逻辑失控，应改为执行器分派表：

```text
note       → NoteActionService
mcp        → MCP executor
filesystem → FileActionService
app        → AppLaunchService
chain      → LaunchChainService
chat       → ChatDeliveryService
```

每个执行器统一返回 `ActionResult`，并负责：

- 执行前复核资源身份和授权租约。
- 记录开始时间与执行状态。
- 区分 completed、failed、not_executed 和 unknown。
- 返回撤销能力与不可撤销原因。
- 不把尚未验证的副作用报告为完成。

同一动作的幂等、执行账本和重复确认保护继续复用现有机制。

### 13.6 启动协调器

`LaunchChainService` 不负责理解自然语言，只接收冻结后的启动计划：

```text
LaunchPlan(
  chain_id,
  starter_app_identity,
  target_app_identity,
  trigger,
  detection_rules,
  readiness_rules,
  parameters,
  grant_lease_ids,
  plan_digest
)
```

执行器先验证 `plan_digest`，再按顺序执行。模型不能修改已经生成的计划，也不能在两个确定性步骤之间替换应用或参数。

Windows 进程和窗口检测优先使用已有 `ctypes` 风格实现，避免为了基础启动链立即引入大型依赖。UI Automation 使用现有 `pywinauto`，但必须封装在独立适配层中，避免核心启动逻辑依赖控件细节。

### 13.7 授权与启动界面

Web 设置页新增“桌面能力”分区，包含：

- 授权目录与能力。
- 应用索引和允许启动清单。
- 中转启动链。
- 活动中的短期租约。
- 最近启动和执行回执。

桌面壳层增加原生目录选择能力，通过 QWebChannel 返回绝对路径，替代当前输入绝对路径的弹窗。浏览器模式保留手动路径输入和严格校验。

聊天流新增两类内联卡：

- 合并授权卡：仅本次、保存到项目、永久允许、取消。
- 启动进度卡：预检、启动中转、等待目标、打开项目、定位会话、完成或失败。

### 13.8 测试与验收

每个切片至少包含：

- schema 迁移和旧数据兼容。
- 路径逃逸、符号链接、硬链接和敏感目录拒绝。
- 文件身份变化和确认前变化拒绝。
- 重复确认只执行一次。
- 失败和 `unknown` 状态不自动重放。
- Web API 契约和设置页交互。

启动链测试使用本机 Python 夹具：父进程脚本启动子进程脚本，验证进程树识别、旧实例排除、超时、取消和目标不唯一。真实 Codex++ 和 UIA 流程作为 Windows 人工冒烟，不依赖 CI 环境。

性能目标：

- 授权后索引在后台运行，不阻塞聊天界面。
- 5 万条元数据的常见文件名搜索在热索引上目标小于 300 ms。
- 启动预检的只读操作并行执行。
- 搜索默认最多返回 5 个候选，避免目录内容进入模型上下文。

- **v13 只建两张授权表**——`access_grants` + `grant_leases`（含 `idx_access_grants_path` 部分唯一索引、`idx_access_grants_status`、`idx_grant_leases_task`、`idx_grant_leases_active`）。`file_catalog` 随 S2、`app_catalog` 随 S4、`launch_chains` 随 S5、`channel_bindings`/`attachments` 随 S6 各自建表，不在这里留没人写的空表。
- **`access_grants` 是唯一事实源**——`get_workspace()/set_workspace()/clear_workspace()` 改为"带 `legacy_workspace = 1` 标记的那一行"的兼容适配器；v12 的单行 `workspace_grants` 提升一次（能力只补 `fs-read/fs-write/fs-search`，删除与外发从未被授予过），并且**每次启动都重查一次旧表**，所以 v13 之前导出的归档恢复进来不会丢授权；提升后旧行强制 `enabled = 0`，已撤销的工作区不会被下一次启动复活。
- **凭据目录在授权环节就拒**——`.ssh/.aws/.azure/.gnupg/.kube/.docker/.codex` 与整个用户主目录默认不能成为授权目录；`allow_sensitive=True` 是唯一的例外，且覆盖位写在行上（`sensitivity_override`）供审计。路径与目录身份的判定抽到 `path_safety.py` 单点持有，笔记写入用 `NoteGuard` 只在其之上加 `.md/.txt` 白名单，两条链不会再各写一套规则。
- **本轮不做 Web API**——`/api/access` 与授权中心界面按 R5 等 Pixso 画板放行；服务层是 `access_control.py`（`AccessControlService` 的授权/撤销/身份复核/租约发放与消费/任务收尾，`state_report()` 只读诊断），`doctor.py` 新增 `Access grants` 检查（WARN 级，绝不写库——只读自检不能把"目录已漂移"看成"现在又好了"）。

租约按 §4.1 落地并加了执行侧复核：一次租约只绑一个任务、一种能力、TTL ≤900 秒、操作 ≤50 次、资源 ≤32 个，`use_lease()` 每次都重读授权状态、能力集合与目录身份，预算在 `UPDATE` 语句内部判定因此并发只放行剩余次数。§13.3 要求的 v12→v13 迁移用例与迁移前备份用例都在 `tests/test_companion_access_control.py`。
