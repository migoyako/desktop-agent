## 1A. RAG 参考项目取证（`C:\Users\黄家禄\PycharmProjects\course05-acp`，用户 2026-11-02 指定）

用户给的路径指向该项目的 `.venv`，实际代码在 `.venv` 里的章节目录（`ch01`–`ch10`、`util`）与项目根的 `docs/`（原始 PDF/DOCX）、`base/`（已转好的 Markdown）、`knowledge/`（已持久化的索引）。它是课程工程，不是可移植的库；下面只记会影响本计划的六条事实。

## 4. 已定的四个问题（Q1–Q4）与风险

- **Q1（已定：复用 `sources`，2026-11-02）** 文档命中**复用现有"来源"通道**：文档片段作为一类来源出现在右栏「来源」里，每条带**文档名 + 块序号**，点击定位。选它的依据是参考项目每个范例都直接展示 `response.source_nodes`（§1A 第 6 条）与 M15 立下的"每条内容可溯源、可删除"原则——出处不是可选项。**"新开一个「文档」分区"虽语义更清楚，但那是 15 块已审核画板里没有的形状，按 K4 必须先补画板，故本轮不选**；落地在**切片 2**：`sources` 的语义从"搜索结果"扩到"搜索结果 + 文档片段"，界面沿用画板已有形状。
- **Q2（已定：独立 `config/mcp_keys.json`，2026-11-02）** MCP 服务器的 token/headers 存**独立密钥文件**，与模型密钥的 `config/keys.json` 分开；界面只回 `mask_secret()` 形状，**库里不存凭据**。依据：参考项目把 bearer token 留在进程环境变量里、从不落库（`ch06/Test07_mcp_http_clirnt.py:20`）；入库会让备份与 zip 导出携带凭据，与"导出不含 `keys.json`"的既有承诺冲突。落地时要一并覆盖：`mcp_keys.json` 的原子合并写（照 `config.py` 对 `keys.json` 的做法）、`doctor.py` 只报"存在/缺失与权限"而不报内容、`maintenance` 的导出名单**不含**它、错误文案不回显 token（照 `web/upstream.py` 的形状）。
- **Q3（已定：a，2026-11-02）** 检索方式是否按参考项目升级为向量。**用户看过参考后选 a = 维持 FTS5 词法**，K1 由此确认，切片 1/2 按现计划推进。三档留档以免被再次翻案时重做调研：
